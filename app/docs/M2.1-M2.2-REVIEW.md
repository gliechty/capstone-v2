# M2.1–M2.2 review

> Current status (2026-10-12): M2.1–M2.2 were human-accepted, as recorded in EXECUTION_PLAN.md. Below is the historical implementation/verification record; its pending-authorization wording is superseded by that plan and the M2.7 review.

## Implemented boundary

The normal `/assessment` route uses the versioned `config/capstone-v1` snapshot. All seven entities remain separate, with explicit TypeScript records and strict Zod schemas. The server adapter validates file hashes, shapes, identities and references before constructing a minimal browser catalog. A malformed snapshot fails the build; it never substitutes mock questions. The optional inactive-reference diagnostic is emitted during build.

The deterministic domain has no framework, Zod, filesystem or browser dependencies. Its selector preserves the October 2 v1 workflow's active/industry/market-or-location/size filters and stable ascending priority order. Buyer and business goal do not participate. Equal priorities retain source row order; category regrouping is intentionally absent.

The existing reducer/context and session-storage adapter are retained. Sessions now carry schema version 3 and a combined canonical-config/setup-vocabulary version. Earlier snapshots under the existing storage key receive an incompatibility warning; employee counts and free-text buyer/goals are not silently reinterpreted. Selecting a revised business context preserves answers for still-selected IDs and removes answers to deselected questions on Start. Missing or invalid drafts remain unanswered; no normalization or scoring is performed.

## Setup and presentation decisions

- All six controlled setup fields use the preserved Appsmith widget vocabularies in `config/assessment-setup-v1.json`, with source hash and widget identities. Only Company name and Subindustry are free text. The actual v1 location/market widgets contain ten regions; unlike the broader validation list, they do not offer a combined `EU/UK` option. Regions are never inferred from countries.
- Company size stores the selected v1 employee-band value directly (legacy spacing retained; labels use en dashes). The count-to-band conversion is removed. Subindustry, buyer and goal remain collected context without new selection rules.
- Target-market checkboxes permit one or two explicit region values. Click order records primary/secondary identity; removing the primary promotes the remaining choice. Checked chips and labeled Remove actions remain available at the limit. Validation rejects duplicate/unknown/three-market snapshots. The selector receives the same region values and applies the same methodology.
- Active AnswerScales supply option labels and display order. Numeric unit labels use metric metadata only. No benchmark resolution or calculations are implemented.
- The browser catalog excludes scoring parameters, weights and document content. Config is public research data, but only required presentation/selection fields cross this boundary.
- M1 mock questions remain solely an isolated unit-test fixture. Results remain clearly labeled fixed mock data, unrelated to canonical answers.

## Dataset and validation

See [CONFIG-MIGRATION.md](CONFIG-MIGRATION.md) and `config/document-identity-map.json` for all nine identity decisions. There are 161 questions (138 active), 39 answer-scale rows, 62 benchmark rows, 42 multiplier rules, five category-weight rows, 44 documents and 428 chunks.

Decimal source lexemes remain strings, preserving precision. Converting priorities/display order for ordering is not scoring. The scoring numeric policy and calculation trace remain future M2 work. Schemas validate supported representations and references without repairing data or adding inferred caps. Benchmark identity includes its group type/value; answer-scale identity includes its option.

Known source issue: inactive question `I-045` references absent metric `managed_land_hectares`. The source row is retained and reported as a diagnostic. Active broken metric/scale references fail loading. This is not a scoring fallback.

The snapshot is a build input. Rebuilding is required to publish any new config version. A future deliberate config edit must use a new version identity and refresh the manifest; deployment does not read BUILD_PACK or require a database. LF-normalized snapshot hashes allow Windows/Linux checkouts; source hashes retain original byte identity. Next file tracing includes the config snapshot for Node deployments.
