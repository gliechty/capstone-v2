# M3.6 — Retrieval accuracy, performance and efficiency evaluation

## Status and purpose

**PLANNED — owner request, 2026-10-13.** This note extends the LlamaIndex/LangChain experiment in `EXECUTION_PLAN.md`, under M3.6. It defines a future test package and its required evidence; it does not report completed experiments or authorize live calls, deployment, production adoption or a scoring change.

Evaluate whether broader retrieval, vector/embedding search or hybrid search improves recommendations compared with the native implementation. The eight-document limit is a baseline tuning setting, not a permanent architectural requirement. The user-facing objective remains complete, validated recommendations in **under 10 seconds under documented normal conditions**, with useful, supported advice.

The required deliverable is a **detailed, reproducible test-results report**, suitable for Professor Guo, plus an accessible summary for the project's future "How it works" section. A dependency installation, demo, single timing or passing schema validator is not sufficient evidence.

## Questions to answer

1. Does the early eight-document shortlist exclude useful evidence?
2. Can searching more of the corpus improve evidence coverage while keeping the final model briefing concise?
3. Do embeddings or hybrid retrieval improve relevance beyond a broader native/keyword baseline?
4. What do LlamaIndex and LangChain contribute independently of changes to retrieval algorithms, prompts or models?
5. Which approach provides the best measured balance of recommendation quality, response time, computing resources, cost and maintenance effort?

## Prerequisites and boundaries

- Establish and preserve the native M3 baseline, accepted deterministic Golden results and documented stable-ID join differences.
- Reconcile legacy SME metadata before freezing comparison inputs. Explicitly account for Additional Context / Requirements (`notes`), revenue band and country. Use identical populated/blank fields across variants; never manufacture unavailable context to improve a result.
- Record the corpus and configuration version, eligible/excluded sources, source editions, chunk identities and unresolved provenance limits. Baseline inventory is 44 documents and 428 chunks; report actual counts at execution.
- Preserve scoring formulas, numeric policy, canonical entity semantics and BUILD_PACK. Retrieval experiments must not change assessment scores.
- Keep experimental retrieval/provider adapters separate from the default runtime. Pin package, embedding-model and index versions. A managed vector database is not a prerequisite for this small-corpus experiment.
- Existing provider/model, budget and permitted-data approvals apply to any external generation, embedding, reranking or hosted evaluation calls. Keep credentials and confidential SME material out of published artifacts.

## Comparison design

Separate **how much material is searched**, **how evidence is ranked**, **how much is sent to the model**, and **which framework executes the workflow**.

| Variant | Retrieval experiment | Final evidence control |
| --- | --- | --- |
| A — native baseline | Preserved metadata ranking, eight shortlisted documents, up to eighteen chunks; current stable-ID joins | Record the baseline evidence/token budget |
| B — broader shortlist | Same ranking with sixteen shortlisted documents | Comparable final evidence/token budget |
| C — broader native search | Same ranking across all eligible documents and their chunks | Comparable final evidence/token budget |
| D — vector/embedding search | Search eligible chunk embeddings across the corpus, retaining source applicability/provenance controls | Same packing and validation policy |
| E — hybrid search | Combine keyword and semantic candidates using a documented fusion method | Same packing and validation policy |

These settings are experimental candidates, not claims of optimality. Record any change to document-score inheritance, filters, tie handling, source diversity or candidate counts. If adding reranking, test it as an explicit additional variant on a bounded candidate set and measure its cost.

Do not automatically place every shortlisted document's summary into the prompt. Apply a common final evidence-packing policy, including document metadata, so broader search is not confused with a larger prompt. Record actual tokens and lengths; a fixed chunk count alone does not equal a fixed token budget. Test larger prompt budgets separately after the controlled comparison.

Use the same approved generation model/settings, semantic prompt instructions, output requirements and request contexts. Run a fixed-evidence comparison to isolate framework overhead from retrieval quality. Avoid an exhaustive framework-by-algorithm matrix unless initial results justify it.

## Accuracy and quality evaluation

- Begin with all five Golden SME contexts, then add a small, documented set of distinct cases covering specific buyer requirements, weak assessment areas, nonempty/blank notes, terminology variations and evidence outside the original eight-document shortlist.
- Define expected relevant passages and a scoring rubric before tuning on the evaluation set. Have a human review the labels and disputed cases; use held-out cases for the final comparison. Disclose small-sample limitations and the annotator/reviewer process.
- Measure retrieval **precision at K** (how much retrieved evidence is useful), **recall at K** (how much of the identified relevant evidence was found) and, where graded relevance labels exist, ranking quality such as nDCG. State whether relevance judgments are exhaustive or pooled; do not claim corpus-wide recall from incomplete labels.
- For generated advice, assess claim support from cited passages, citation correctness, coverage of important gaps, SME applicability, practical usefulness and authoritative-score consistency. Report the number of cases/claims assessed and the rubric, not an unexplained "accuracy percentage."
- Include negative cases: wrong source/edition/page, unsupported numerical targets, mismatched metric or units, conflicting source context and irrelevant advice. A percentage occurring somewhere in an evidence bundle does not prove the specific claim or citation is supported.
- Keep deterministic score fidelity and schema/citation-membership checks separate from semantic grounding and human usefulness. An automated or model-based judge may assist review but must not be the sole authority for factual accuracy.
- Show representative successes, failures and per-SME evidence gained/lost. Document whether broader retrieval finds genuinely useful evidence or merely duplicates.

## Speed, resources and algorithmic efficiency

Measure the full path from requesting recommendations to complete, validated output visible to the user. First-token time may be supplementary but is not the completion target.

| Dimension | Required measurements |
| --- | --- |
| User-visible speed | End-to-end median, p95, range and sample count; success, validation-failure, timeout and provider-error counts |
| Stage timings | Query preparation/embedding, candidate retrieval, optional reranking, evidence packing, provider generation, validation and rendering/network overhead |
| Computing resources | CPU time and peak memory where measurable; specify process boundaries and any unavailable hosted-provider metrics |
| Search work | Eligible corpus size, candidates examined/returned, reranked candidates, final sources/chunks, similarity/scoring operations where instrumentable |
| Token and financial efficiency | Prompt/output tokens, model calls and generation/embedding/reranking cost per request and per usable result |
| Index lifecycle | One-time ingestion/embedding/index build time and cost, disk/memory size, and update/reindex cost, reported separately from per-request latency |
| Scaling | Baseline corpus plus clearly labeled larger test corpora; latency, memory, indexing cost and retrieval-quality changes as size grows |

Use repeatable runs, documented hardware/runtime/network/provider settings, warm-up policy and predetermined run counts within the approved budget. Distinguish cold starts, warm uncached requests, cached requests and concurrency. Include failed runs in the report; do not calculate an apparently fast system by silently excluding failures or counting rejected output as usable.

If synthetic expansion or duplicates are used to test scale, label them as a performance stress test; they do not establish real-world semantic accuracy on a larger knowledge base. Where feasible, compare approximate vector search with exact search on the small corpus to quantify evidence missed by the index approximation.

Describe the algorithmic work and measured growth as corpus size increases. Distinguish measured efficiency from theoretical complexity; do not claim asymptotic superiority from one small timing result. Report what cannot be measured.

## Review and adoption decision

Select an approach from the measured quality/speed/resource tradeoff. Retaining native retrieval is a valid result if additional machinery does not justify itself. A faster system with poorer grounding is not automatically an improvement; a better retriever that misses the latency target must be reported as such.

Before changing the production/default retrieval policy, present the chosen settings, evidence differences, latency/cost implications and relevant regression results for review. Preserve a versioned native baseline and a simple rollback path. Record demonstrated framework work accurately for the CV without implying unperformed production deployment.
